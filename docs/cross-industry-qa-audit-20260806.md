# 跨產業預約／報名 SaaS QA 與 UX 審查

更新日期：2026-08-06
審查範圍：顧客公開入口、LINE／瀏覽器備援、預約、活動／課程報名、付款、提醒、顧客紀錄中心、後台營運與報表。
審查原則：以目前 `AGENTS.md`、`clinic-booking-spec-v3.md`、70 項標準功能與正式 Railway 公開入口為基準；不把未提供的 LINE、Email、金流或 DNS 憑證驗收結果臆測為已完成。

## 一、結論先行

目前系統已不是單純的預約表單：預約、活動報名、套票／會員、標準付款結構、報到、CRM Lite、報表與品牌隔離的主要骨架都已存在。這些能力在程式碼與公開路由中可以被驗證。

但目前仍不能直接宣稱「已完整支援所有產業」，原因不是缺少頁面數量，而是三個產品層問題：

1. 核心預約仍以 `doctors`、`patients`、`visit_type` 為技術與流程中心。介面已開始改成服務提供者／顧客，但資源型、無指定人員型、團隊輪派型服務仍被迫套用人員預約模型。
2. 預約、報名、付款、報到與顧客紀錄已分別存在，但仍有跨模組的後續動作不完整。顧客可以在 `/my` 看到資料，但報名取消、報到憑證、付款補繳與預約管理尚未全部在同一個入口完成。
3. 成熟產品的差異在「整個預約生命週期」與「營運效率」：外部行事曆衝突、表單／同意資料、候補、週期預約、通知流程、分眾歸因與報表決策，仍有缺口或需外部驗收。

本次已直接處理的低風險修正：

- 預約列表、日曆、顧客端、瀏覽器備援、改期、提醒、Email、Rich Menu 與 LINE 回覆中的醫療專用顯示文字，改為產業中性用語。
- `booked` 待確認預約新增「確認」操作，並在確認後觸發既有 LINE／Email 預約確認通知。
- `/my` 的未來預約增加「管理預約」入口，連回既有取消／改期流程。
- 保留資料庫技術欄位與既有舊版號次流程，避免直接改名造成正式資料或既有部署中斷；舊版號次／進度功能列為隔離與產品範圍待處理項目。

## 二、跨產業情境測試

| 情境 | 目前可走的流程 | 實用性判定 | 主要問題 |
|---|---|---|---|
| 診所／諮詢服務：指定人員、固定時段、取消改期 | 服務 → 人員 → 日期／時段 → 顧客 → 預約 → 提醒 | 可用 | `doctors`／`patients` 技術語意仍在資料層；確認、付款、通知需正式憑證驗收 |
| 美容／髮廊：多服務、多工作人員、不同時長與緩衝 | 服務時長／緩衝 → 人員排程 → 預約 → 顧客歷史 | 部分可用 | 服務與資源有骨架；尚缺服務級取消政策、加購品項、外部行事曆衝突與回訪流程完整度 |
| 健身／教室：團體課、名額、候補、報到、套票 | 活動／課程 → 場次／票種 → 付款／候補 → QR 報到 → 套票 | 可用但分流 | 報名流與預約流尚未完全合併；顧客紀錄可查看，但報名後續管理入口仍分散 |
| 顧問／家教：一對一服務、首次／再次服務、Email 提醒 | 服務 → 服務提供者 → 可用時段 → 預約 → Email | 部分可用 | 首次／再次服務可中性顯示，但生日欄位與人員必填未必適合所有品牌；缺少預約前自訂 intake 表單 |
| 場地／設備租借：無指定人員、以資源容量為主 | 資源 → 服務 → 時段／容量 → 預約 | 不足 | 目前公開預約流程仍要求 `doctor_id`；資源型品牌無法自然地只選場地／設備 |
| 多分店／多地點：同品牌多地點、不同人員與時區 | 品牌 → 入口 → 服務／人員／資源 → 預約 | 不足 | 目前以品牌隔離為主，尚未形成一級 `location` 模型與地點級營業時間／報表 |

### 建議的共同主流程

```text
品牌入口
  → 選擇目的（預約服務／報名活動／會員與套票）
  → 選服務或活動
  → 依品牌設定選人員、資源、地點與時段
  → 顧客資料／自訂表單／條款同意
  → 名額與資源衝突檢查
  → 付款或訂金（若啟用）
  → 確認通知與顧客紀錄
  → 改期／取消／候補／報到／完成
  → CRM Lite 分眾與營運報表
```

目前程式已涵蓋其中多數節點，但「選服務後決定需要什麼資料、誰／什麼資源負責、付款後如何回到同一筆顧客紀錄」仍應以同一個可配置流程實作，而不是各模組各自完成。

## 三、目前已發現的缺口與優先級

### P0：跨產業產品定位與主要流程阻塞

| 缺口 | 證據／現況 | 影響 | 驗收條件 |
|---|---|---|---|
| 預約流程仍硬依賴服務提供者 | `app/api/booking/config`、`availability`、`reserve` 與 RPC 仍使用 `doctor_id` | 場地租借、設備租借、無指定人員服務無法自然使用 | 服務可設定「必須指定人員／可指定／不需要人員」；資源型服務可只依資源與容量完成預約 |
| 服務與活動的顧客生命週期未完全合流 | `/my` 已能列出預約、報名、套票，但報名查詢、取消、QR 與補款仍分散至 `/register/my`、報名結果頁等入口 | 顧客看得到紀錄，卻不一定能完成下一個動作 | 每一筆紀錄都有依狀態顯示的下一步：付款、取消、改期、查看 QR、重新報名或聯絡品牌 |
| 號次／進度為醫療型舊流程 | `/admin/queue`、`/q`、LINE progress action 與 `lib/queue.ts` 仍存在 | 跨產業品牌可能看到不適用的功能或被誤導 | 以品牌／產業設定隔離或停用；標準導覽不顯示，公開入口不能預設暴露醫療語意；保留舊資料相容測試 |
| 服務型預約缺少可配置的顧客資料表單 | 預約主要固定姓名、電話、生日、Email 與 `visit_type`；報名才有自訂欄位 | 顧問、教室、租借、活動前問卷需要另外人工補資料 | 服務可設定欄位、必填、同意條款與資料保存規則；送出前顯示預覽，後台可查詢且不超出角色個資權限 |

### P1：營運可用性與成熟度

| 缺口 | 目前不足 | 建議 |
|---|---|---|
| 外部行事曆衝突 | 目前可加入 Google／ICS，但不是雙向同步；外部忙碌時間不會自動阻擋 | 先做 Google／Outlook busy-time 讀取，再做建立／更新同步；列為另行報價項目仍符合 v3 |
| 週期／重複預約 | 目前以單筆預約與改期為主 | 加入預約系列、例外日期、系列取消與通知去重；不能用多筆獨立預約假裝完成 |
| 預約候補 | 活動／場次有候補；一般時間制預約未形成同等候補流程 | 服務級啟用候補、候補順位、釋出名額、通知期限與逾時轉下一位 |
| 服務級規則 | 取消／改期主要以品牌設定；服務時長與緩衝已有 | 補上服務級取消提前時間、訂金規則、顧客表單、提醒策略與是否允許改期 |
| 批次營運操作 | 後台目前以單筆確認、完成、未到、取消為主 | 支援依日期／服務／人員篩選後批次確認、取消、匯出與通知，並留下每筆稽核紀錄 |
| 顧客資料整併 | CRM Lite、預約、報名、會員資料能互相查詢，但欄位與入口仍帶 `patient` 相容語意 | UI 統一使用顧客；技術欄位先保留，新增服務／活動／會員時間軸的共用查詢層 |
| 通知作業 | LINE／Email 與 delivery log 已有；仍缺少通知模板版本、測試發送、排程預覽與逐筆重試操作 | 建立「模板 → 觸發 → 收件人 → 投遞結果 → 重試」可追查流程 |
| CRM Lite 可操作性 | 已有規則式分眾、自動化、預覽與投遞摘要 | 補上啟用前實際受眾數、排除條件、測試收件人、頻率上限、停止原因與轉換結果 |
| 報表決策能力 | 已有預約／報名／付款／通知／匿名漏斗／匯出 | 補上轉換率、來源／UTM、服務利用率、取消提前量、回訪率、收入與退款對照；退款／對帳需依金流範圍確認 |
| 設定引導 | 功能頁已多，但新品牌建立後仍缺少依序完成的 onboarding checklist | 以「品牌 → 服務 → 人員／資源 → 排程 → 入口 → 通知 → 測試預約」引導首次設定 |

### P2：規模化與加值能力

- 多地點／分店、地點時區、地點級人員與資源。
- 公開 API／Webhook 與標準事件訂閱。
- 多語系與 RTL 等介面國際化。
- 退款、對帳、發票、POS 或指定金流商。
- 進階 CRM 管線、客服工單、AI 分群與 AI 行銷自動化。

這些不應在本輪直接混入標準功能；須依既有「七項另行報價／清單外客製」政策個別確認。

## 五、測試驗收腳本

以下腳本應在每一個新品牌至少以「一對一服務」與「團體／活動」各跑一次；資源型品牌再追加第三組。

### A. 一對一服務

1. 建立服務：名稱、分類、時長、緩衝、價格、是否需要人員、是否需要資源。
2. 建立兩名服務提供者，為同一週日建立兩段以上服務時段，另建立一個例外停用日期。
3. 用顧客端選服務，驗證空檔只呈現未滿且符合前置／最長天數規則的時間。
4. 兩個顧客同時搶最後名額，確認只有一筆成功；被拒者看到可理解訊息。
5. 後台確認預約，確認顧客收到一次通知；重複操作不得重複發送。
6. 顧客從 `/my` 進入管理預約，完成改期與取消；歷史仍保留且 CRM／稽核可查。
7. 完成、未出席、訂金待付款／付款成功／逾時釋放，均能在列表、顧客紀錄與報表對得上。

### B. 團體課程／活動

1. 建立活動、兩個場次、免費與付費票種、自訂必填欄位、條款版本與報名截止時間。
2. 額滿後新增候補，釋出名額後只提升一位並發一次通知；逾時能繼續處理下一位。
3. 顧客完成付款，查看統一顧客紀錄、報名狀態與 QR 報到憑證。
4. 現場用 QR、姓名、電話、報名編號各測一次；重複報到需回傳 duplicate 而不新增紀錄。
5. 管理者匯出名單，確認品牌、日期、付款與顧客個資權限均正確。

### C. 資源／設備型服務

1. 建立不指定服務提供者、只需要場地或設備的服務。
2. 兩筆重疊預約同一資源，第二筆應被容量／衝突規則拒絕。
3. 資源停用後，既有歷史保留，新預約不可再取得該資源。
4. 報表能依服務、資源、日期查詢使用量與取消，不要求虛構的醫療人員資料。

## 六、本次審查的驗證證據與限制

- 正式 Railway 公開入口已以品牌範圍查驗：首頁、瀏覽器備援、活動報名、會員、顧客紀錄、預約設定 API 與活動 API 均回 HTTP 200。
- 目前公開頁多由 client component 載入互動內容，因此單純下載 HTML 不足以代替手機／桌面互動驗收；需在可登入的品牌資料與正式第三方憑證下跑上面的腳本。
- 本次沒有執行真實金流扣款、LINE 推播、Email 投遞、DNS／自訂網域切換或瀏覽器相機報到，因為這些需要外部帳號、商店號、憑證或使用者裝置權限；它們保持「外部待驗收」，不宣稱完成。

## 七、建議開發順序

1. 先完成 P0：服務型預約的「人員可選／可不選」模型、統一顧客後續動作、號次舊流程隔離、自訂服務表單。
2. 再完成 P1：外部行事曆、服務級規則、預約候補、批次後台、通知模板／測試發送、CRM Lite 實際受眾與轉換、報表決策欄位。
3. 最後才評估 P2 加值與清單外客製，並同步更新 v3 技術規格、資料遷移、測試案例與合約範圍。

在 P0 完成前，產品可以作為「有預約／報名骨架的多品牌 SaaS」進行內部測試，但不應對外宣稱已達到成熟跨產業預約／報名平台的完整度。
