# Reservation System 產品重整基線（M0）

> 更新日期：2026-08-11  
> 上位規則：`AGENTS.md`、`clinic-booking-spec-v3.md`  
> 目的：凍結本次產品重整的功能邊界、現況證據與路由歸屬，避免以新增功能掩蓋既有產品結構問題。

## 1. 狀態定義

| 狀態 | 判定方式 |
|---|---|
| 已實作 | 主要程式流程存在，且有本機或資料庫證據；不代表第三方正式環境已驗收。 |
| 部分完成 | 已有頁面、資料或流程，但未達 v3 或本次目標的完整生命週期。 |
| 未完成 | v3 明確要求，但目前沒有可操作的完整實作。 |
| 外部待驗收 | 程式契約存在，仍需 LINE、金流、Email、DNS、Cron 或正式品牌資料證明。 |
| 加值項目 | v3 列為另行報價，不得混入本次標準產品重整。 |
| 明確不做 | `AGENTS.md`／v3 排除，未經確認不得開發。 |
| 舊版相容 | 僅為舊資料或舊流程保留，不可作為標準產品入口或完成證據。 |

## 2. 本次重整的核心判定

目前系統不是缺少大量資料表或頁面，而是「預約營運、活動報名、顧客會員、LINE 通訊」四個產品領域以功能清單方式攤平。現有主要交易能力大多已存在，但以下 P0 缺口會阻擋目標完成：

| 領域 | 現況 | 本次必補缺口 | 主要證據 |
|---|---|---|---|
| 預約 | 部分完成 | v3 要求時間制／場次制預約候補；目前沒有獨立的預約候補資料、原子遞補與通知閉環。 | `app/api/booking/`、`supabase/schema.sql` |
| 活動報名 | 已實作／外部待驗收 | 保留既有活動候補、付款與 QR 報到，不得與新的預約候補混為同一狀態機。 | `app/api/registration/`、`waitlist_entries` |
| 顧客與會員 | 已實作／外部待驗收 | 後台入口需依品牌是否啟用會員功能顯示；顧客端仍需收斂成單一 LIFF 顧客中心。 | `/admin/patients`、`/admin/memberships`、`/my` |
| CRM Lite | 已實作／外部待驗收 | 顧客資料必須常駐可用；分眾與自動化入口依品牌啟用狀態顯示。 | `/admin/crm`、`crm_*` tables |
| LINE／LIFF | 部分完成 | destination 已可對應品牌，但 LINE Login Channel／LIFF ID 仍是單一部署環境設定，尚未形成共享渠道與品牌獨立渠道的明確契約。 | `lib/line.ts`、`lib/useLiff.ts`、`.env.example` |
| Rich Menu | 部分完成 | 現行每品牌只有一筆設定，儲存已發布選單會直接更新線上版本；缺草稿、版本、驗證、回復、可用性 label 與完整品牌深連結。 | `/admin/richmenu`、`line_richmenu` |
| 後台導覽 | 部分完成 | 入口仍依技術模組分成多群；需收斂為六個工作區與一個設定中心，並由角色及品牌啟用狀態控制。 | `components/AdminNav.tsx` |
| 品牌啟用 | 部分完成 | 目前工作台只有品牌、服務、排程三步；目標要求七步就緒檢查、警告與阻擋原因。 | `/admin/dashboard` |
| 正式驗收 | 外部待驗收 | LINE、Email、金流、DNS、Cron、備份／還原及雙品牌攻擊仍須依 runbook 取得外部證據。 | `docs/acceptance-matrix.md` |

## 3. 標準產品領域

所有既有標準功能必須歸入下列領域，不新增第七個日常營運領域：

1. **今日工作台**：今日預約、待確認、待付款、候補、報到、通知失敗與未讀訊息。
2. **預約營運**：預約日曆、預約清單、取消、改期、狀態與預約候補。
3. **活動與報名**：活動、場次、票種、表單、報名名單、活動候補與 QR 報到。
4. **顧客與會員**：顧客、互動時間軸、會員、套票、優惠碼、分眾與規則式自動化。
5. **訊息中心**：LINE 客服對話、訊息素材、自動回覆、通知與投遞狀態。
6. **報表**：預約、報名、未到、候補填補、付款、會員與 CRM 摘要。
7. **設定中心**：品牌、服務、資源、排程、入口、LINE／LIFF、Rich Menu、付款、Email、網域、團隊、權限與稽核。

系統管理者總控台是獨立產品殼層，不屬於品牌後台七個區域。

## 5. 身分與權限基線

| 管理身份／員工類型 | 本次產品語意 | 現況與處置 |
|---|---|---|
| 系統管理者 | 全 SaaS 治理 | 管理品牌、方案、系統人員、營運健康、跨品牌報表、稽核與系統設定。 |
| 品牌管理者 | 單一或多個授權品牌 | 管理品牌日常營運、設定、品牌人員及其權限。 |
| 系統員工 | 系統工作權限接受者 | 由系統管理者逐項授予品牌管理、方案、營運健康、報表、稽核或設定權限；不能管理系統人員。 |
| 品牌員工 | 品牌工作權限接受者 | 由品牌管理者授予品牌管理、營運操作或指定服務提供者權限；不能管理品牌人員。 |

資料庫舊值 `owner / admin / frontdesk / staff / provider` 僅保留為 RLS 相容映射，不再作為產品身份或後台顯示名稱。

## 6. 品牌啟用與公開狀態不可混用

- 「標準功能全數開放」表示品牌可以啟用，不代表所有品牌永久顯示所有入口。
- 模組啟用控制後台產品領域是否出現；公開發布控制顧客是否可使用公開入口，兩者必須分開。
- 例如活動模組可先啟用並建立活動，但 `public_registration_enabled=false` 時仍不可公開報名。
- `brand_entitlements.feature_flags` 只標記七項加值合作，不得拿來關閉 v3 標準功能。
- 直接輸入停用模組 URL 時，server 必須驗證並回到設定中心或顯示停用狀態，不能只靠前端隱藏連結。

具體模組契約、角色矩陣與目標導覽定義於 `docs/product-information-architecture.md`。

## 7. 凍結範圍

### 加值項目

- 指定金流商、完整退款與對帳。
- 行事曆雙向同步。
- 對外 API／Webhook。
- 白標、多語系。
- 分院／分店及特殊產業流程。

### 明確不做

- 健保掛號、HIS／病歷交換。
- 標準產品叫號／即時看診進度。
- 完整 CRM、AI 行銷自動化。
- 評價導流、公開活動市集、廣告投放與流量分潤。
- POS、庫存、薪資抽成等本次目標未列能力。

### 本次目標之後另行決策

- 週期性預約、家人／團體代訂、多服務與加購、未到取消費。
