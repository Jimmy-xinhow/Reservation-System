# XINHOW 預約與報名 SaaS：系統 Review、UI/UX 優化與產品路線

初版日期：2026-08-13
最近更新：2026-09-02
驗證環境：既有 Railway staging 證據＋本輪本機型別、契約與 Playwright 局部驗收
規格基準：`AGENTS.md`、`clinic-booking-spec-v3.md`

## 1. 執行結論

目前系統已具備成為多品牌預約與報名 SaaS 的核心完整度，前後端沒有發現 P0 等級的租戶隔離、前端洩漏 service role 或角色越權缺口。真正影響上手與營運的問題不是功能不足，而是先前的資訊架構把「建立品牌、品牌資料、預約規則、入口、金流、通知、網域」放在過長頁面，登入與拒絕權限後的落點也不符合工作流程。

本輪已完成：

- 品牌登入後改進入「今日工作台」，不再落在預約清單。
- 品牌員工進入未授權頁面時，安全返回工作台並顯示原因與申請權限方式。
- 系統員工進入未授權頁面時，安全返回系統總覽並顯示原因。
- 系統控制台拆成「營運總覽／建立新品牌／品牌交付狀態」。
- 品牌設定拆成「品牌資料／預約與入口規則／付款與通知／網址與網域／進階操作」。
- 設定頁加入 LINE、金流、Email、網域就緒狀態；LINE 不再只以啟用開關冒充正式驗證完成。
- 修正文案中「訂金不串金流」與標準金流實作互相矛盾的問題。
- 系統總控台返回品牌後台的落點改為今日工作台。

正式上線仍有外部驗收條件：品牌 LINE Channel／LIFF、Email 寄件網域、綠界或藍新正式商店、DNS 自訂網域都必須使用實際帳號與正式密鑰完成 smoke test；本地 build 或 staging 空設定不能代替此證據。

## 2. 前後端 Review

### 2.1 已確認的強項

- 多租戶資料一律以 `clinic_id` 綁定，後台以品牌成員與 active brand context 決定範圍。
- 顧客端只呼叫 Next.js API；service role 保留在 server-only 模組。
- LINE ID token、webhook 簽章、金流回呼與租戶對應都有 server 邊界。
- 預約與報名容量使用資料庫鎖與原子 RPC，取消保留歷史，不以刪除代替狀態。
- Rich Menu 使用草稿、驗證、發布、回復與事件紀錄，不會因儲存草稿直接覆蓋正式版。
- 系統管理者與品牌管理者是兩個管理身分；系統員工與品牌員工使用細權限，不再增加混亂的第三種管理角色。
- 套件正式依賴 `npm audit --omit=dev` 結果為 0 個已知漏洞。
- TypeScript strict type-check 與現有契約測試通過。

## 3. 角色與操作流程

### 3.1 系統管理者

1. 從共用登入頁選「系統管理後台」。
2. 先看營運總覽、平台健康、跨品牌報表與稽核。
3. 進入「建立新品牌」，輸入品牌資料與品牌管理者 Email。
4. 建立後轉到「品牌交付狀態」，確認品牌管理者、短網址、服務、排程與顧客入口完成度。
5. 由「系統人員與權限」新增系統員工，只授予工作需要的權限。
6. 系統管理者不代替品牌處理預約、顧客或訊息內容。

### 3.2 系統員工

1. 從共用登入頁選「系統管理後台」。
2. 導覽只顯示被授權的平台工作區。
3. 若從舊連結或網址進入未授權功能，系統返回總覽並顯示申請權限說明。
4. 系統員工不能建立其他系統管理者，也不會因前端隱藏失效而取得 server 權限。

### 3.3 品牌管理者

1. 從共用登入頁選「品牌營運後台」，登入後直接進入今日工作台。
2. 依七步啟用中心完成品牌資料、服務／活動、人員／資源／排程、規則、LINE／Rich Menu、通知／付款與正式測試。
3. 每日先處理待確認、待付款、通知失敗與未到，再查看日曆和報表。
4. 品牌設定以工作區分段，不必在同一長頁尋找不同領域的欄位。
5. 由「團隊與權限」新增品牌員工，按實際職務授權。

### 3.4 品牌員工

1. 登入後直接進入今日工作台，只看已授權的營運模組。
2. 櫃檯可授予日常營運；服務提供者可只授予指派範圍；行銷或報表人員只授予必要頁面。
3. 未授權功能不出現在導覽；直接輸入網址時也會被 server 拒絕並得到清楚說明。

## 4. 市場對照與定位

台灣輕量 LINE 預約產品主要訴求「免下載 App、LINE 自助預約、自動提醒、會員與簡單營運」。國際成熟產品再加入資料匯入、自訂表單、重複／多服務預約、員工排班與權限、no-show 政策、POS、行銷與多渠道整合。

XINHOW 現階段的差異化不應是「功能最多」，而應定位為：

> 以 LINE 為主要入口、同時支援瀏覽器備援的多品牌預約、活動報名與 CRM Lite 營運平台。

目前具有明顯差異的能力：

- 同一平台同時支援時間制與場次制預約。
- 預約、活動票券、候補、QR 報到、套票與優惠碼在同一租戶邊界。
- 系統層與品牌層管理分開，員工採最小權限。
- Rich Menu 不是單張圖片，而是有版本、草稿、正式發布、Alias 頁籤、排程、回復與成效。
- LINE、瀏覽器、自訂網址、嵌入與自訂網域共用同一顧客任務契約。

| 渠道測試中心 | 已分開保存 LINE、LIFF、Email、金流與公開入口檢查結果 | 渠道啟用成功率與失敗修復時間 |
| 預約來源與轉換總覽 | 已整合 Rich Menu 區域點擊、網站來源與匿名完成事件 | 預約／報名完成率與每來源轉換率 |
| 交班清單 | 已可依狀態、分類、優先度與負責人篩選 | 待處理平均時間與逾期事項 |

### Phase 2：成交與回訪

| 功能 | 目前狀態 | 保留邊界 |
|---|---|---|
| 預約自訂表單與同意欄位 | 已支援文字、長文字、日期、選項、勾選與必填同意 | 不作病歷或 HIS |
| 重複預約 | 已由顧客選擇連續週次，先確認每週容量後原子建立；任一週失敗就整組不建立 | 訂金啟用時維持逐筆預約與付款 |
| 多服務加購 | 已支援主服務的加購項目，加購分鐘納入容量檢查，價格保存於預約快照 | 尚未擴成跨人員、多張訂單的服務組合 |
| 非 AI 訊息範本庫 | 已有可預覽、變數白名單與測試送出的訊息範本 | 不擴成完整 CRM 或 AI 行銷 |
| 快速再預約 | 我的預約可帶回最近服務與人員，再重新查詢可用時段 | 不略過容量、身分或品牌範圍檢查 |

### Phase 3：另行商業與架構評估

以下在市場上有價值，但已超出 v3 標準範圍或會顯著改變產品：

- Google／Outlook 雙向行事曆同步。
- 完整退款、對帳與財務結算。
- POS、商品庫存、員工分潤與薪資。
- 多語系、進階白牌與原生管理 App。
- 評價導流、推薦獎勵與公開活動市集。
- AI 行銷文案、AI 自動分眾與全自動投放。

這些不能直接塞回目前導覽；應各自建立商業目標、資料模型、權限與驗收標準，再決定是否做成加購模組。

## 6. 建議執行順序

1. 已完成：staging migration、Railway 部署、DB lint、公開 smoke、新 RPC 與本輪手機溢位局部驗收。
2. 釐清並消除建置警告；先以 Next.js、Supabase 與 Railway 官方做法確認遠端字型、Edge Runtime 與 Nixpacks secret 警告，不為消除警告任意更換技術棧。
3. 將 staging release gate 合併到預設分支，建立 GitHub `staging` environment，經授權後安全加入必要 secrets，再首次執行四身分頁面驗收。
4. 使用實際 LINE／LIFF／Rich Menu、Email、測試金流與 DNS 完成外部渠道證據。
5. 以三個試用品牌觀察「首次可預約時間、設定頁退出率、權限求助、預約完成率」。
6. 依付費意願決定雙向行事曆、退款對帳、POS、分潤、多語與白牌等加購。
