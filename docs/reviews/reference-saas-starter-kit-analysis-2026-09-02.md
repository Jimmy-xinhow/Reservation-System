# 參考案例與成熟開源專案採用基準

日期：2026-09-02
參考案例：[2026 SaaS Starter Kit 展示頁](https://portfolio-cbf.pages.dev/works/2026-saas-starter-kit/)
本專案規格基準：`AGENTS.md`、`clinic-booking-spec-v3.md`

## 1. 結論

參考案例適合借鏡的是「內容安排與操作流程」，不是直接作為本專案的工程底座。它把會員、預約、優惠、活動、LINE 會員卡與後台管理放在同一個產品故事中，顧客先看常用服務，管理者再進入資料與設定，方向與本專案相近。

截至本次檢查，該案例對應的公開程式庫仍是很新的展示型專案：GitHub 顯示 0 stars、0 forks，且未看到可確認的授權檔。因此只參考畫面層級、資訊順序與使用情境，不複製程式碼、圖片或品牌素材，也不把它當作安全、多品牌隔離或交易流程的證據。

本專案的功能範圍已比該案例更廣；本輪需要補的重點是把既有能力整理成使用者看得懂、找得到、操作得完的介面，而不是再增加另一套功能或技術框架。

## 2. 可參考的內容與流程

| 參考案例做法 | 本專案採用方式 | 狀態 |
|---|---|---|
| 顧客登入後先看到常用任務 | `/book` 預設顯示「顧客服務中心」，集中預約、我的預約、活動、票券、會員、客服與品牌資訊 | 已完成 |
| 主要動作放在第一屏 | 顧客首頁優先顯示「立即預約」；若品牌暫停預約，改以「我的預約」作主要動作 | 已完成 |
| 個人資料與交易紀錄分開 | 我的預約、活動票券、會員套票分成獨立任務，不把所有內容塞在一張卡片 | 已完成 |
| 狀態用短文字與標籤呈現 | 預約、報名、付款、會員與渠道狀態統一顯示繁體中文；原始系統值只放在「技術資訊」 | 已完成 |
| 後台使用固定導覽與頁面標題 | 後台依今日營運、顧客、活動、會員、訊息、報表、品牌設定分組，頁首說明本頁能完成的工作 | 已完成 |
| 較少使用者懂的內容延後顯示 | 品牌代碼、資料隔離規則、LINE 路由代碼與錯誤追查值改放可展開的「技術資訊」 | 已完成 |

## 3. 功能範圍比較

| 領域 | 參考案例公開展示 | 本專案目前設計 |
|---|---|---|
| 預約 | 服務提供者、範本、容量、審核與取消 | 時間制與場次制、首次服務延長、提供者可選／必選／純資源、候補、取消、改期與重複預約 |
| 活動 | 活動與優惠內容 | 活動場次、票種、優惠碼、候補、付款、報到條碼與現場報到 |
| 會員 | 會員等級、點數、優惠券與 LINE 會員卡 | 會員方案、套票堂數紀錄、預約／活動扣抵、到期通知；目前不含點數制與通用會員 QR 卡 |
| 通知與渠道 | LINE 會員卡及查詢入口 | 各品牌 LINE／LIFF、Rich Menu 版本與排程、LINE／Email 提醒、瀏覽器備援、自訂網址、嵌入與自訂網域 |
| 營運 | 後台儀表板、角色與稽核 | 品牌與系統兩層管理、細權限、CRM Lite、來源轉換、報表、稽核、渠道測試與交付狀態 |
| 交易安全 | 公開頁面未提供足夠證據 | 預約／報名容量鎖、付款回呼重送保護、取消恢復權益、品牌資料隔離與顧客身分驗證 |

「更完善」以可驗收的流程與資料安全為準，不以畫面數量或功能名稱判定。正式 LINE、Email、金流與 DNS 仍須取得實際帳號證據後，才能宣告外部流程完成。

## 4. 成熟開源參考來源

下列專案主要作設計與流程參考。這一輪沒有增加正式環境套件，也沒有替換 Next.js、Supabase 或 Tailwind；只新增 `@playwright/test` 作為 CI 瀏覽器驗收工具。

| 開源來源 | 成熟度快照（2026-09-02） | 參考範圍 | 本專案採用原則 |
|---|---|---|---|
| [shadcn/ui](https://ui.shadcn.com/docs) | 約 123k GitHub stars、MIT、持續更新 | 表單、按鈕、卡片、狀態標籤、資料表與可展開區塊 | 採用一致、可組合、可閱讀的元件規則；不為了外觀一次引入整套相依套件 |
| [PatternFly](https://www.patternfly.org/components/page/design-guidelines/) | Red Hat 維護的企業產品設計系統，現行文件為 6.6.1 | 固定頁首、主導覽、內容分區、響應式間距、無障礙與後台文案 | 用於後台頁面結構與內容規則；不替換 Tailwind，也不混用第二套 CSS 框架 |
| [Cal.diy](https://github.com/calcom/cal.diy) | 約 45k GitHub stars、MIT、16k 以上 commits；官方明示社群版不建議直接作正式商用託管底座 | 預約類型、可用時間、時區、取消與改期流程 | 只核對成熟預約流程，不搬用其企業版功能或部署架構 |
| [Twenty CRM](https://github.com/twentyhq/twenty) | 約 47k GitHub stars、70 以上 releases | 顧客列表、詳細資料、互動時間軸、篩選、匯入與權限呈現 | 只參考 CRM Lite 的資訊層級與操作順序，不複製程式碼或擴成完整 CRM |
| [Playwright](https://playwright.dev/) | Microsoft 維護的開源瀏覽器自動化工具 | 桌機／手機畫面、流程、權限導覽與水平溢位驗收 | 只加入開發相依，用於本機與 CI 驗收，不進入正式執行內容 |

成熟度不是只看 stars；還要同時確認維護時間、近期更新、正式授權、文件、測試與是否真正符合本專案技術棧。任何要加入的依賴仍須先說明原因，不能因為參考案例用了就直接安裝。

## 5. 明確不直接採用

- 點數制度、通用優惠券中心、會員 QR 身分卡、Google／Email OTP 綁定與多語系：目前不在 v3 標準範圍，必須先確認產品需求。
- 參考案例的配色、圖像、文案與程式碼：沒有足夠授權證據，不直接複製。
- Cal.diy 或 Twenty 的完整資料模型：兩者範圍與本專案不同，直接搬入會破壞既有 `clinic_id` 品牌隔離和設定驅動原則。
- 新的 UI 框架：現有 Tailwind 元件已能完成這輪一致化；沒有必要增加維護成本。
